03 / AI WRITING GAPS → SYSTEM RESPONSES

先看清 AI 的短板，再决定怎样使用它。

AI 可以加速局部工作，却不能替作者完成判断。这个项目把常见失控点拆开，并用流程、证据和人工确认把它们放回正确的位置。

“AI 是概率抽卡器，最终质量取决于使用工具的人。”— AI 写作问题汇总中的核心判断
常见问题AI 直出最容易在哪些地方失控
01

长文会衰减，设定会失忆

一次输出有可控上限，长对话越拉越长，人物口吻、前文事实和场景细节越容易漂移。续写只能反复摘取前文，依然可能出现 OOC 与前后矛盾。

上下文丢失人设漂移
02

逻辑漏洞不会自动消失

AI 能指出“看起来像问题”的地方，却不可靠地判断因果、伏笔、动机和生活逻辑。机械降神、危机不升级、前后反转互相打架，往往会在自查后继续存在。

逻辑断裂自查失真
03

套路旧，AI 味重

训练数据带来高频结构与陈词滥调。华丽空泛、官方书面词、同义堆叠、机械标点和“像……一样”的比喻，都会让文本显得像未经处理的模型输出。

概率抽卡文本痕迹
04

剧本需要画面，模型常给小说

心理解释、环境渲染和表情堆叠并不等于可拍的动作。台词可能啰嗦、干巴、脱离人设，场景缺少具体调度，制作时只能逐句返工。

镜头不清台词返工
05

大纲、梗和换元不能一键交付

自动整理会损失情节和衔接，核心事件容易回到老套路。直接把原文翻成剧本，也只是逐集搬运，无法自动获得短剧或漫剧所需的冲突密度。

信息损失核心事件老套
06

经验、市场与合规无法外包

模型没有作者的生活阅历、审美和真实体感，也不能替你做选题取舍、平台判断和版权边界判断。它还可能胡编来源、擅自加戏，或把敏感内容推向风险区。

判断力缺口合规风险
HOW THIS PROJECT RESPONDS

把“让 AI 写完”，改成“让系统帮助你做对决定”。

项目如何应对
◌

上下文工程

项目事实、人物 Bible、素材引用、岗位记忆和阶段产物分层保存。每个 Agent 只接收当前任务需要的证据，减少串项目、忘设定和无关信息污染。

对应：长文衰减 · 人设漂移
⌘

分阶段编排与专业岗位

把选题、人物、结构、正文、拆书、换元和质检拆成可交接的岗位与阶段。不同格式使用不同的任务边界，不让一个窗口承担整部作品。

对应：小说化 · 大纲丢情节 · 一键改编
✓

质量门禁与交付证据

用 Schema、字数、结构、钩子、逻辑线索、格式和合规规则做门禁，并保存 Run、Receipt 与版本，让“模型说完成”变成可以查看、比较和复核的交付。

对应：逻辑漏洞 · 格式错误 · 假完成
◉

人机协作与候选比较

作者可以比较多个候选、采纳某个版本、指出缺口，再把结果交给下游 Agent。系统把选择权留在作者手里，AI 负责扩展方案和执行局部工作。

对应：判断力缺口 · 过度依赖
▤

知识库、拆书与来源追踪

把公开剧本、小说样例和方法论导入知识库，生成分析报告、引用片段和桥段沉淀。素材先成为可追溯证据，再服务于仿写、换元和人物／场景／动机置换。

对应：素材不足 · 套路化 · 盲目找剧情
↻

可恢复的长任务执行

租约、心跳、checkpoint、重试和暂停恢复，让任务遇到限流、掉线或人工中断时保留已有产物。失败会暴露在流程里，而不是悄悄变成一份残稿。

对应：长任务失控 · 重复生成断层

04 / TOKEN ECONOMY & RELIABILITY

少发送无关上下文，把预算花在真正的创作上。

节省 Token 不是把内容偷偷删掉，而是让稳定部分可缓存、让变化部分按任务加载，让每次调用都知道自己为什么需要这些信息。

为什么普通工具容易越用越贵？

把完整系统提示、所有工具 Schema、整段聊天记录和全部资料塞进每一轮，会重复支付同一批输入 Token；上下文越长，模型越容易忽略真正相关的内容，返工和无脑重试又会继续放大成本。

固定前缀缓存
＋任务相关增量
＋可追踪的重试
◫

提示词缓存友好

System Prompt 被拆成固定顺序的 Slot。角色、Skill 元信息、工具索引和合同组成稳定前缀，并计算 prefix hash；同一岗位连续执行时，静态部分不必每轮重新组织，能更好利用模型的 KV / Prompt Cache。

作用：减少重复输入 · 提高多轮复用率
⌁

Agent、Skill、Tool 动态加载

Agent 默认只看到 Skill 名称和摘要，需要时才读取正文；任务相关的 Skill Catalog 排在动态后缀，工具也按已知能力优先、未知能力再搜索。这样不会把 137 个 Skill 和整套工具 Schema 一起塞进每一次调用。

作用：最小上下文 · 更少工具干扰
◌

上下文分层与预算

角色、合同、核心事实、经验教训、个性化偏好和运行时信息分别占位，并有字符预算。必需约束超预算会停下来要求拆分或整理，不会静默截断关键设定。

作用：控制长度 · 保住关键约束
◎

用户偏好变成可复用配置

用户明确表达的文风、节奏、题材禁区、交付格式、常用模型和反馈可以沉淀到 personalization Slot。后续任务只注入与当前项目相关的偏好，避免每次重新解释，也避免把别的项目习惯串进来。

作用：减少重复沟通 · 支持个性化工作台
⌘

用来源与引用降低幻觉

知识库引用保留来源、版本和范围，项目事实与分析报告成为可回查的 Context Ref。Agent 先检索相关证据再生成，Gate 和 Receipt 记录它用了什么，发现编造时可以沿着证据链定位。

作用：少凭空补全 · 方便复核与纠错
↻

全流程透明，从失败点恢复

Run Trace 会展示 Agent、工具、产物、Gate、失败和人工确认发生在哪里。遇到限流、掉线或暂停时，系统从最近的 checkpoint 继续，只重跑未完成的阶段，复用已经通过的产物、引用和缓存前缀，不必从头重发整段上下文。

作用：定位失败 · 少重跑 · 少发 Token

怎样理解“比别的工具省 Token”？

它指的是系统减少了重复提示词、无关工具定义、整段历史和失败重试带来的浪费。实际节省量取决于模型供应商是否支持缓存、任务长度、缓存命中率、调用次数和你选择的上下文范围，页面不承诺固定百分比。

05 / READ BEFORE YOU RUN

先了解这些限制，再把任务交给系统。

这是当前版本的真实使用边界。提前缩小能力范围、降低并发和拆短任务，通常比失败后反复重试更省 Token。

!
正常功能验收已过（含 S11_DONE），但系统仍处于 Early Preview。

核心错误已经修复，剩余风险主要集中在共享契约、并行开发后的字段一致性、权限派生上下文、重复错误策略和长任务稳定性。模型、Provider、工具搜索和上下文压缩仍可能在边界条件下失败。

01

tool_search 可能反复找不到工具

当工具名、参数或 Agent 权限不匹配时，模型可能连续搜索、换关键词、再搜索。这类空转会消耗大量 Token，却没有推进任务。

建议按自己的工作流删减 tools、agents、skills，只保留常用和当前阶段需要的能力；已知工具直接调用，连续两轮找不到就停下来改任务边界。
02

Subagents 仍可能失败

子任务会受到模型返回不完整、并发闸、Provider 限流、强顺序依赖和上下文过大的影响。当前策略适合独立候选或只读侦查，不适合把整本书拆给大量写手并行硬灌。

建议每次并行控制在 2–3 个，嵌套深度 1；大纲未确认、正文有强依赖时保持串行。
03

中国模型优先 DeepSeek

本项目一次任务会连续触发编排、Agent、工具循环和质检。历史经验显示，DeepSeek 更适合作为正式写稿主力；MiniMax 和其他易限流 API 在多轮工具调用时更容易排队或返回 429。

建议DeepSeek 全局并发从 6–8 起步；使用 MiniMax 时先把 workerConcurrencyCap、任务组和子任务并发都降到 ≤2。
04

MiniMax 的失败率不要被低估

项目历史日志观察到约 8.9% 的 MiniMax 429“准备重试”记录，接近你在实际使用中感受到的约 10% 波动。它不是完整 attempt 级失败率，重试后成功和未记录的上游尝试都可能改变真实比例。

建议把 MiniMax 当备用或小流量对照，减少 Fleet 和 fanout；不要因为增加 Worker 就假设任务会更快。
05

中文、表情与英文会让 Token 估算失真

中文字符、emoji、混合 JSON、英文标识符和工具参数的计数方式不同，字符预算不能直接等同于模型 Token。上下文压缩可能仍超出有效窗口，摘要也可能在错误时机触发。

建议不要把估算值当硬上限；长任务先拆段，保留项目事实和产物引用，发现摘要遗漏或早期摘要被遗忘时，直接新开窗口并从已保存产物继续。
06

长任务请控制在可恢复范围

任务超过约 15 分钟后，模型往返、工具调用、压缩和限流叠加，漂移与失败概率都会上升。步骤太多时，即使系统保留了 checkpoint，也可能需要人工重新确认上下文。

建议单个任务尽量控制在 15 分钟以内、800 步以内；写完阶段产物就停下来验收，必要时开新窗口继续。
SUBAGENTS / FAILURE GUIDE

Subagents 失败时，先对照错误类型。

下面的“建议值”是起步档，不是 Provider 配额承诺；先看 Run Trace 的错误码和失败子任务，再决定是否重跑。

输出

返回不完整或结果不可用

子 Agent 可能只返回半截文本、没有 handoff，或要求 terminal proof 但证明不可用。不要把父 Agent 的一句“已完成”当作交付证据。

限流

全局闸 / Provider 429

本机等待超时、上游 RPM、TPM、5 小时窗或周窗都可能让子任务排队、重试后失败；提高并发只会放大突发。

硬限制

并行超过 3 或深度超过 1

当前运行时硬限制是单次 parallel 最多 3 个、嵌套深度 1。超过时会出现 parallel_size_exceeded 或 depth_exceeded，不是模型能力不足。

能力

嵌套不可用或角色不允许

某些流水线成员会隐藏 subagent_spawn；子任务默认不能再派生，scout 还是只读。出现 nested_unavailable 时应改任务边界，不要重复调用。

上下文

引用无效、过大或绑定失败

并行任务共享的 contextRefs 必须来自当前项目、带版本和范围；引用过多、过长、版本失配或快照 ID 不支持，都可能导致 invalid_delegated_context。

权限

工具 / 项目 / 角色范围不足

scout 不能写产物，planner 工具有限，reviewer 需要明确候选引用；缺项目、工具不在 allowlist 或角色映射缺失时，子任务会启动失败或无法交付。

状态

子任务非 succeeded

取消、超时、模型错误、Gate 未通过或 worker 崩溃都会让父任务收到 failed / cancelled / unknown。并行结果会保留失败原因，不能当成全量成功。

持久化

写入证据未落盘

子任务执行成功但步骤或 delegation 结果持久化失败时，系统会拒绝把它伪装成成功；先检查 checkpoint / receipt，再决定恢复或人工确认。

强顺序依赖的正确用法大纲未确认、上一集产物未验收、同一共享产物会互相覆盖时保持串行；Subagents 更适合独立创意候选、只读侦查、规划和评审 fanout，不适合把全书正文同时灌给多个写手。
CONFIG QUICK START

按模型改哪几个值？

先改全局闸，再改 Fleet，最后决定是否开 Subagents；三层会叠加，不能只改一层。

  1. DeepSeek 日常：workerConcurrencyCap=6–8，Fleet maxConcurrency=4，每次 Subagents 2–3，嵌套深度 1。
  2. MiniMax / 其它易限流 API：全局闸和 Fleet 先设 ≤2，Subagents 1–2，正文串行；观察 429、排队超时和任务调用数后再逐步加。
  3. 环境兜底：AGENT_WORKER_CONCURRENCY 只在设置页没有写入时作默认，同时也是每个 Worker 的启动并发上限；改大后要重启 Worker。需要平滑突发可调 LLM_MIN_REQUEST_INTERVAL_S，等待名额看 LLM_ADMISSION_WAIT_S。
  4. CLI / Web：设置 → 流量治理。DeepSeek 示例：pnpm xzm settings set-llm-traffic --body '{"workerConcurrencyCap":8,"fleetDefaultConcurrency":4}'；易限流 Provider 示例改为 {"workerConcurrencyCap":2,"fleetDefaultConcurrency":2}。已有 Fleet 的显式并发需单独核对。

RECOVERY ORDER

失败后的 6 步

  1. 先看 Run Trace、错误码、子任务状态和最近 checkpoint。
  2. 把 parallel fanout 降到 1–2，易限流 Provider 先停掉大 Fleet。
  3. 有依赖的 Stage 改串行，先验收上游产物再继续。
  4. 缩小 contextRefs，保留当前项目的版本、UTF-16 start/end 偏移和精确 quote；最多 8 条引用、每条最多 4,000 字符、合计最多 12,000 字符。
  5. 检查项目存在、role 映射、tools allowlist 和信任/确认状态。
  6. 结果不确定时先核对已结束子任务的 run ID、receipt 和 artifact 版本，再从 checkpoint 恢复或只重跑缺失项，不要原样盲重试。

KNOWN ENGINEERING RISKS

目前还没有完全收敛的四类问题

P0

Schema / 契约漂移

六个 Cursor 窗口并行推进后，工具参数、Skill 示例和前后端 DTO 可能混用 `input_schema` 与 `inputSchema`。模型按文档调用，仍可能被另一层拒绝。

P1

撤权后的派生上下文

新请求会拦截失效权限，但旧摘要、缓存和子 Agent 结果若已混入撤权内容，全路径重建与清理仍是后续设计。

P1

重复错误后的策略升级

同一个错误指纹出现多次时，停止原样重试、切换路径或升级人工的策略还不够完善，模型可能继续搜工具、换参数和空转。

提示

大文件定位可能失败

模型读取大文件时可能找不到目标段落、误判已读范围或只记住摘要。请提供章节、行号、关键词或精确文件范围，避免让模型反复全文搜索。

SAFE START

第一次使用前，先做这 5 个动作。

  1. 删掉当前阶段不用的 tools、agents、skills。
  2. DeepSeek 从低并发开始，MiniMax 先设 ≤2。
  3. 先跑一个核心梗、人物小传或单场景，不要直接开全集。
  4. 盯住 Run Trace、失败节点、摘要覆盖范围和最近 checkpoint。
  5. 摘要开始遗漏早期事实时，新开窗口，从已保存产物和引用继续。
