## 1. 先说结论（读这一段就够开工）

| 场景 | 建议 |
|------|------|
| **正式写稿 / 多 Agent 流水线** | **只用 DeepSeek**（日常 `deepseek-flash`，难推理再开 `deepseek-v4-pro`） |
| MiniMax / 其它国内 API | 可作备用或冒烟；**本项目短时间多轮 tool loop 极易 429 / 额度窗限流**，不适合当主力 |
| 本机实测 | DeepSeek 写稿链路限流压力小；MiniMax 等常在并发一开就撞墙 |
| **任务要花多少钱** | 见 **§6**：单次选题/正文中位大约 **几分～一毛多**；写到约 10 集量级 DeepSeek Flash 峰时有缓存大约 **¥3～¥7+**（无缓存悲观可到十几元） |

根因不是「别的模型一定差」，而是：**本仓库一次任务会在短时间内打很多次模型**（编排 → 多同事 → 工具循环 → 质检）。官方并发/RPM/订阅额度窗一旦偏紧，就会表现为「限流」。DeepSeek 账号级并发额度对这种用法更宽松（见下文官方链接）。

## 2. 哪些参数管「并发」

本项目有**三层**并发，不要只改一个就以为能扛住上游限流。

### 2.1 本机 LLM 流量闸（最重要，用户常改）

| 项 | 说明 |
|----|------|
| 是什么 | 全局「同时在飞」的模型请求数上限（PA / Agent / Fleet / 子任务共用） |
| 范围 | **1–16** |
| Web | **设置 → 流量治理 → Worker 并发上限** |
| CLI | `pnpm xzm settings llm-traffic` |
| 写入 | `pnpm xzm settings set-llm-traffic --body '{"workerConcurrencyCap":8}'` |
| 环境变量兜底 | `.env` 里 `AGENT_WORKER_CONCURRENCY`（**仅当设置页尚未写入时**作默认；改设置页优先生效） |
| 相关 | `LLM_ADMISSION_WAIT_S`（等闸超时）、`LLM_MIN_REQUEST_INTERVAL_S`（请求起步间隔，平滑突发） |

**推荐取值**

| 当前模型 | `llm-traffic` cap | 说明 |
|----------|-------------------|------|
| DeepSeek Flash | **6～8** | 够用；不必开到官方 2500 |
| MiniMax / 其它易限流 API | **≤2** | 开大只会更快 429 |

### 2.2 Fleet / 任务组并发

| 项 | 说明 |
|----|------|
| 是什么 | 一组里多个同事并列跑时的组内并发 |
| 默认 | `max_concurrency` **默认 4**；成员最多约 **4** |
| 哪里改 | 创建 Fleet / 任务组时的 `maxConcurrency`（API / UI）；仍会被本机 `llm-traffic` **再夹一层** |
| 建议 | DeepSeek：可到 4；MiniMax：≤2 |

### 2.3 Subagent 并行（开发者 / 进阶）


| 项 | 说明 |
|----|------|
| 是什么 | **某一个** Agent Run 内部 `subagent_spawn` 再拆子题 |
| 默认 | 并行最多 **3**，嵌套深度 **1** |
| 哪里改 | `packages/agent-runtime/src/subagents.ts` 的 `DEFAULT_SUBAGENT_POLICY`（一般用户不用动） |
| 注意 | 批量**正文**仍优先串行；并行留给独立候选 |

**Subagent 适合干什么（和「批量」的关系）**

| 适合 `subagent_spawn` | 不适合 |
|----------------------|--------|
| 彼此独立的**创意候选**（多梗、多换元、多钩子、多选题方向） | 一书/全集正文「一次拆很多写手硬灌」 |
| 只读侦查：搜 bible / KB / 热点摘要后再汇总结论 | 有强顺序依赖的 Stage（未 ack 大纲就并行开写） |
| 主 Agent 太大时：scout → 浓缩报告，主会话不塞全文 | 代替人做扫榜、拆剧、建桥段库（见下「素材积累」） |

> 下表「Subagent」= 是否适合用 Run 内并行子任务做 fanout；「状态」含**规划中**项（未来会实现，以产品为准）。

#### 先分两类

| 类型 | 该不该 AI 批量 | 说明 |
|------|----------------|------|
| **素材积累**（扫榜、拆剧、桥段库、阅片） | **否** | 课里说「素材积累 AI 帮不了」→ 人积累；KB/Tropes 只承载，不伪批量替代 |
| **灵感候选 fanout**（一次多条 → 人筛 / 截取 / 融合） | **是** | 一次出 10/50/100 → **人筛选**后再采纳进项目 |

#### 需要批量生成的场景

| # | 场景 | 典型规模 | 并发 / Subagent 建议 | 状态（本仓） |
|---|------|----------|----------------------|--------------|
| 1 | **核心梗** fanout | 一次 **10～100**；再人筛（含 100 字测试）；四步造梗、老梗×元素缝合同路 | 候选彼此独立 → **适合** Subagent / 组内并行（默认并行 ≤3）；凑数后主 Agent 汇总 | **已有**：`topic.core_hook_batch` 等 |
| 1b | 核心梗 **Critic 批量打分** | 对候选列表打分排序，**不是**只出一条就开写 | 可与 batch 串成「生成 → 评审」；评审也可拆子任务但注意别打满闸 | **已有**：`topic.core_hook_critic` 等 |
| 2 | **换元多方案** | ≥**3**，可到几十 / 上百；人选后再定稿 | 同核心梗：fanout 可并行，**采纳前**须人闸 | **已有**：`swap.master` + count |
| 3 | **爽点 / 虐点大事件池** | 先扩 **10→100** 再排序灌粗纲 | 池内条目独立 → 适合并行扩；灌纲前排序 / 人工裁剪 | **已有**：`struct.cool_expand` 等 |
| 4 | **集尾钩多备选** | 每集 **N** 个钩子，人挑 | 按集拆子任务或单 Run 内多候选；**不要**与正文批写抢满并发 | **已有**：`hook.episode_alts` 等 |
| 5 | **热点选题卡** | 多条方向，不一次钉死一个 | 可并行出多卡；注意 **Search 按次费**（§5.1 / §6.3） | **已有**：`topic.hotspot` |
| 6 | **灵感四层扩写** | 同一灵感升维出多候选 | 适合 Subagent 按层 / 按分支扩；产品侧入口仍偏轻 | **部分已有** / **规划加强** fanout |
| 7 | **桥段变体** | 同一桥段多变体 | 适合系统化 fanout（Subagent 或 batch job） | **规划中**（现多走 KB → 换元复用） |
| 8 | **IP 单元批量表** | 多单元并列，人判松紧 | 单元彼此独立 → 适合并行；勿一次改编全书 | **部分已有** / **规划完整工位** |

#### 明确不要「一次灌完」的

| 不要批量硬灌 | 正确用法 | 并发注意 |
|--------------|----------|----------|
| 全书 / 全集正文 | 分块；默认前 **3** 集串行再 QA（`orch.batch_writer`） | **禁止**靠把 Subagent 开很大来「并行写满 10 集」 |
| 人设 / 大纲「一键全书」 | Stage 锁 + 人工 ack 后再开正文批 | Fleet ≤4 且仍受 `llm-traffic` 夹层 |
| 用 AI **替代**扫榜 / 拆剧 / 建桥段库 | 人积累；AI 只做摘要级热点、拆书报告辅助 | 热点可多条选题卡，≠代替阅片量 |

#### 和限流的关系（实用）

1. **fanout 场景**（表中 1–8）：DeepSeek 下可开 `llm-traffic` **6～8** + Subagent 并行 **3**；易限流 API 先降到 **≤2**。  
2. **正文批写**：保持串行；429 时先缩 fanout，而不是先怪模型「写不快」。  
3. **未来**桥段变体 / 灵感风暴 / IP 批量表若做成大规模并行，仍走同一套闸——上线时以设置页 cap 为准，本文会随产品更新状态列。

> **一句话**：批量的是**可筛选的创意面**（梗、换元、爽虐池、钩子、选题）；**不该**用 AI 替代人的素材积累，也**不该**批量硬灌全书成稿。  


并行会**叠乘**本机 `llm-traffic` 与上游 RPM：DeepSeek 下 fanout 可到默认 3；易限流 API 应先把 cap 降到 ≤2，再少开子任务。

### 2.4 其它与「打模型节奏」相关的环境变量

见根目录 [`.env.example`](../.env.example)：

| 变量 | 作用 |
|------|------|
| `AGENT_WORKER_CONCURRENCY` | Worker 并发默认（见上） |
| `LLM_ADMISSION_WAIT_S` | 等容量闸的秒数 |
| `LLM_MIN_REQUEST_INTERVAL_S` | 跨进程请求最小间隔（默认 0.3；`0` 关闭） |
| `AGENT_MODEL_RETRY_MAX_WAIT_MS` / `AGENT_MODEL_RETRY_MAX_ATTEMPTS` | 被明确拒绝时本轮内等待重试（不重放已执行的写工具） |
| `AGENT_LLM_TIMEOUT_S` | 单次模型请求超时 |

## 3. 哪些参数管「自动回复 / 自动批准 / 吵不吵」

这里说的不是「模型自己回一句你好」，而是：**确认卡、飞书打扰、信任门**——写稿流水线里真正影响「会不会自动往下跑」的开关。

### 3.1 Personal Agent 确认卡（自动批准）

| 变量 / 配置 | 作用 | 默认（`.env.example`） |
|-------------|------|------------------------|
| `PERSONAL_AGENT_CONFIRM_TIMEOUT_MIN` | 确认超时（分钟）；到点未操作则按自动应答策略处理 | `10` |
| `PERSONAL_AGENT_AUTO_RESPOND` | 是否**自动批准继续**（与 Web 共用） | `true` |

环境变量全集见 [`.env.example`](../.env.example) 飞书段；飞书服务说明见 [`services/feishu/README.md`](../services/feishu/README.md)。

> 想「关键点必须人手点」：把 `PERSONAL_AGENT_AUTO_RESPOND=false`，并适当加大超时，避免误以为系统卡死。

### 3.2 飞书群聊是否自动接话

| 变量                              | 作用                                         | 建议                            |
| ------------------------------- | ------------------------------------------ | ----------------------------- |
| `FEISHU_GROUP_POLICY`           | `mention`＝群聊需 @ 机器人才响应；`always`＝群内任意消息都进总编 | **默认 `mention`**；`always` 噪高大 |
| `FEISHU_PROGRESS_VERBOSE`       | `false` 合并批进度；`true` 逐条 tool 进度            | 默认 `false`，少刷屏                |
| `FEISHU_WATCHDOG_STUCK_MINUTES` | Run 卡住超 N 分钟飞书告警                           | 默认 `15`                       |

### 3.3 同事 / Bot：信任与通知（产品内配置）

| 配置 | 在哪 | 作用 |
|------|------|------|
| `trust_level`（0–3） | AI 同事详情 → **信任** | 写操作是否要你确认（`trust_policy.requires_confirm`） |
| `notify_policy` | 同上：`important` / `all` / `none` | 代你操作系统时**何时推送**（审计始终记） |

文档位置：[`docs/agents/12-runtime-contract.md`](../docs/agents/12-runtime-contract.md) §7（Personal Agent / notify_policy）。

### 5.2 MiniMax（对照；本场景易限流）

| 项 | 内容 |
|----|------|
| 限流 | https://platform.minimax.io/docs/guides/rate-limits |
| M Plan | https://platform.minimax.io/docs/m-plan/faq |
| 国内域名常见入口 | https://platform.minimaxi.com （Key 须与域名平台一致） |

## 6. 各任务成本估算（本机 `.data/sessions` 实测）

> **数据口径（2026-11-21）**  
>
> - 来源：本仓库 `.data/sessions/sessions/*.jsonl` 里 `type=usage` 事件（**236** 次有用量的 Agent Run）  
> - 合计约 **3024 万 tokens**（输入约 **96%** / 输出约 **4%**）；缓存命中率合计约 **75%**（单 Run 内多轮常更高，长尾/换前缀会拉低）  
> - 单价按上文 DeepSeek Flash（峰/谷）；**有缓存**列用真实 `prompt_cache_hit/miss`；**无缓存悲观**把全部输入当 miss  

> - 金额由原美元测算 × **7.2** 折成 **¥**（约到分或角，便于扫读）  
> - 下表「单次」取该任务族 Run 的 **p50（中位）**；重任务看 **p90**。不是报价承诺，换模型/返工次数会变  
> - 本机精确账单：`pnpm xzm usage summary`

### 6.3 读数怎么用

1. **日常报预算**：优先看「峰·有缓存」——本仓库 Slot 布局就是为抬高命中。

3. **限流敏感**：同一流水线在 MiniMax 上更容易先撞 **RPM/额度窗**（见 §5.2），所以仍建议 DeepSeek。

## 7. 遇到 429 / 限流时怎么做

1. **确认当前服务商**：设置页是否仍是 MiniMax？→ 切回 **DeepSeek**。
2. **降并发**：流量治理 cap → DeepSeek 用 6～8；其它 API → **1～2**。
3. **缩 Fleet / 别盲目并行正文**：候选可并行，正文串行。
4. **看用量页**：缓存命中是否过低（前缀是否被打乱）大概率时间戳的原因。
5. **查上游额度**：MiniMax M Plan 是否撞 5 小时/周窗；Kimi 是否低充值档。
6. 本仓库有限流排队与重试，但**不能发明上游没有的配额**——闸降下来才是正解。

## 9. 本机实测：请求频率与 429 口径

> 以下由根 README「并发与限流实测」迁入（2026-11-21 本地快照）。混有历史测试、恢复与重跑，**不能直接当生产成功率**。

### 9.1 先把四种「数量」分开

| 数量 | 控制内容 | 当前约束 |
| --- | --- | --- |
| Worker 并发 | 一个 Worker 同时执行多少个顶层任务 | 环境硬上限与 Governor 有效值取较小值，范围 1–16 |
| 全局 LLM 闸 | 总编、Agent、子任务共享的在途模型操作名额 | `workerConcurrencyCap`；遇限流可自适应下调 |
| 任务组并发 | 同组有多少成员推进 | 单组 `maxConcurrency`，仍受全局闸约束 |
| Subagents 并行 | 单个父 Run 一次拆出多少子任务 | `maxParallel=3`、`maxDepth=1`；不绕过全局闸 |

网关在一个名额内可能进行重试或切换 Provider，所以本机名额数也不是完整的供应商计费次数。群聊成员人数更不能当作模型并发。

### 9.2 短时间到底发了多少请求

从 596 个历史 Session 文件中，仅对能按 Run / turn 关联 `model_call → usage` 的样本统计起步时间；按 Run 的模型字段归属。表中只含可归属的两个模型子集；旧记录、失败但未返回 usage 的尝试与网关内部重试可能缺失。

| 可配对样本中的滚动峰值 | DeepSeek Flash | MiniMax M3.1 Flash |
| --- | ---: | ---: |
| 样本数 | 750 | 445 |
| 任意 1 秒内的模型轮次起步 | 2 | 4 |
| 任意 10 秒内的模型轮次起步 | 8 | 9 |
| 任意 60 秒内的模型轮次起步 | 23 | 32 |
| 同一 Run 任意 60 秒内的起步 | 18 | 16 |

**这些是频率，不是同时在途的 HTTP 连接数，也不是两个模型的对照跑分。** 不同模型用了不同任务、版本和时段。

另有一次独立的 MiniMax 三人编组验收，记录到 **3 个同时有效的模型请求租约**，三位成员任务共同执行约 29.69 秒，且该轮未观察到上游限流。这证明特定配置下确实有并行成功，并不证明账号只能并发 3 个或能够无限并发。见 [该轮机器记录](../docs/agents/2026-11-19-minimax-reliability-results.json)。

带耗时字段的代理链路样本（含排队/重试，**不是纯推理速度**）：

| 指标 | DeepSeek Flash | MiniMax M3.1 Flash |
| --- | ---: | ---: |
| 带耗时记录数 | 646 | 455 |
| 请求链路耗时中位数 | 1.71 秒 | 3.75 秒 |
| 95% 请求在此时间内完成 | 13.18 秒 | 26.52 秒 |
| 输入 Token 中位数 | 约 1.5 万 | 约 6500 |
| 输入 Token 的 P95 | 约 3.8 万 | 约 2.4 万 |

有用量事件的会话，调用次数中位数约 **6**、P95 约 **22**。明确的 `subagent_spawn` 仅 **11** 次，其中并行两次均为 **2** 个子任务 → **不支持把 Subagents 扩到 5–10**。

### 9.3 161 条 429 占总请求多少

在同一份历史日志 `.xzm/logs/studio-loop-acceptance-api.log` 中：

| 观测项 | 数量 |
| --- | ---: |
| `/llm/agent-chat` 已结束代理请求，HTTP 200 | 1,719 |
| `/llm/chat` 已结束代理请求，HTTP 200 | 56 |
| `/llm/agent-chat` 已结束代理请求，HTTP 502 | 37 |
| 上述模型代理 POST 合计 | **1,812** |
| MiniMax 上游 429 的「准备重试」日志行 | **161** |

`161 ÷ 1,812 ≈ 8.89%`，只能表达为：**每 100 条已结束的模型代理 POST，观察到约 8.9 条上游 429 重试记录。**

**它不是上游请求失败率。** 一个代理请求可以对应多次上游尝试，重试后仍可能返回 200；最后一次不再重试的 429 未必计入这 161 条。目前无法精确回答「所有 MiniMax 上游尝试中有多少比例返回 429」——需要完整 attempt 级日志。公开侧保留 [聚合数据](./session-metrics-2026-11-21.json) 与 [统计方法](./session-audit-2026-11-21.md)。

## 10. M4 / 32GB：建议怎样配

LLM 推理在云端，本机主要负担上下文、工具、数据库和界面。没有与 Session 同步的历史资源峰值，因此以下是**起步建议，不是已验证的硬件极限**。当前工作站为 10 核 M4 / 32GB；快照中已有 Swap 存量，不能据此认定项目正在持续换页。

**建议日常档：DeepSeek 全局 8 / Worker 4 / 任务组 4 / Subagents 每次 2–3 / 深度 1。** MiniMax 有历史 429 时先用 2 / 2 / 2 / 子任务 1–2。

| 项目 | DeepSeek 日常 | DeepSeek 多独立项目 | MiniMax 历史订阅场景保守起点 |
| --- | ---: | ---: | ---: |
| 全局 LLM 并发 | **8** | **12** | **2** |
| 单 Worker 顶层任务并发 | **4** | **6** | **2** |
| 单任务组并发 | **4** | **4** | **2** |
| 每次实际 Subagents 并行 | **2–3** | **3** | **1–2** |
| 子任务嵌套深度 | **1** | **1** | **1** |
| 本地排队等待 | 120 秒 | 120 秒 | 120 秒 |
| 新操作最小入场间隔 | 0.1 秒 | 0.1 秒 | 2 秒起，结合账号限额调整 |
| 模型请求超时 | 600 秒 | 600 秒 | 600 秒 |
| 主 Agent 轮次预算建议 | 32 | 32 | 32 |
| 自适应降并发 | 开启 | 开启 | 开启 |

「多项目档」适合多个**独立**项目一起跑；同一篇正文 / 同一共享产物加并发可能增加协调冲突。侦查 / 规划 / 执行 / 评审子任务现有最大轮次分别是 6 / 4 / 12 / 6。**延长本地排队只减少「等不到名额就报错」，不会提高吞吐。**

DeepSeek 官方 Flash / Pro 账号并发 2500 / 500 远高于本机建议档，详见 [官方并发规则](https://api-docs.deepseek.com/zh-cn/quick_start/rate_limit/)。MiniMax：账号限额不明且有历史 429 → 先 2/2/1–2；确认充值 API 200 RPM 且 429 消失后再试 4/3/2；若是 20 RPM 档，入场间隔建议至少 3.5 秒（网关内部重试不完全经过该闸，**不是严格 RPM 保证**）。额度耗尽时降并发只能减慢消耗。

### 10.1 怎样预估扩大并发后的压力

用带耗时的代理请求链路样本做粗估：DeepSeek 平均约 **4.12 秒**，MiniMax 平均约 **7.35 秒**（含排队/重试）。

```text
无工具等待、持续有请求且耗时不变时：
理论轮次吞吐 ≈ 60 × 全局并发 / 平均占槽秒数
DeepSeek：8 路约 116 次/分；12 路约 175 次/分
MiniMax：2 路约 16 次/分；4 路约 33 次/分
```

这只是容量量级示意，**不是实测成绩或账号权益**。优先从 DeepSeek 8 / Worker 4 起步，用相似任务比较完成时间、429、排队超时、每任务模型调用数、数据库锁与内存压力，再决定是否到 12 / 6。16 路暂不作为默认建议。

### 10.2 配置入口与生效范围

```bash
# 查看，不修改
pnpm xzm settings llm-traffic
pnpm xzm settings governor

# 可选：采用 DeepSeek 日常建议（执行后才会修改设置）
pnpm xzm settings set-llm-traffic \
  --body '{"workerConcurrencyCap":8,"fleetDefaultConcurrency":4,"adaptiveEnabled":true}'
```

| 参数 | 在哪里改 | 生效与边界 |
| --- | --- | --- |
| `workerConcurrencyCap` | Web 设置 → 流量治理，或上述 CLI | 全局请求闸；不覆盖进程硬上限 |
| `fleetDefaultConcurrency` | 流量治理 API / CLI | 默认值；已有任务组显式 `maxConcurrency` 需另行核对 |
| `AGENT_WORKER_CONCURRENCY` | 根 `.env` | Worker 启动硬上限；改后重启相应进程 |
| `LLM_ADMISSION_WAIT_S` / `LLM_MIN_REQUEST_INTERVAL_S` | API 进程环境 | 等待与新操作入场间隔；不是 Provider 专属限额 |
| `AGENT_LLM_TIMEOUT_S` | API 环境 / Settings | 模型请求超时 |
| `AGENT_MAX_TURNS` | Worker 环境 | 顶层任务默认预算；任务显式 `maxTurns` 优先 |
| Subagent 上限与角色轮次 | [`subagents.ts`](../packages/agent-runtime/src/subagents.ts) | 代码策略，无设置页；当前硬上限已是 3 / 深度 1 |
| Provider 故障转移 | 设置 → 流量治理 | 备用已启用、有密钥且兼容任务时才有意义 |

数据库中的服务商设置优先于环境兜底。只改 `LLM_DEFAULT_PROVIDER` 不一定改变已保存的默认服务商；只把 Worker 环境变量改大，也不会越过较小的 Governor 上限。

## 12. 模型选择：要不要换成 Kimi 或 ChatGLM

截至 **2026-11-22**，公开评价更适合决定「值得加入候选测试」，不适合直接证明「换了就一定更好」。本项目已有 DeepSeek / MiniMax 的真实 Session、成本与限流材料，它们仍是最有证据的基线。这里的 **ChatGLM** 指智谱开放平台 GLM 系列 API。

| 候选 | 网上普遍认可的长处 | 对本项目可能有用的地方 | 需要警惕的地方 | 当前建议 |
| --- | --- | --- | --- | --- |
| DeepSeek Flash | 价格低、缓存友好、OpenAI 兼容；本项目样本最多 | 总编、普通 Agent、结构化任务和高频迭代的默认基线 | 不能因便宜就放大并发 | **继续作为默认基线** |
| MiniMax M3/M3.1 系列 | 长上下文、工具/Agent 任务口碑较好 | 长材料整理、复杂规划 | 历史 429、重试放大；长思考增延迟 | **保留作复杂任务候选，先降并发做 A/B** |
| Kimi K2.x/K3 系列 | 长上下文、多步工具、Agent 评价较突出 | 研究、资料交叉、故事图/世界观、跨文件上下文 | 产品/API 名变化快；榜单 ≠ 你的写作质量 | **优先试验，不建议直接全量替换** |
| 智谱 GLM 系列 | 中文表达、结构化调用反馈较多 | 中文改写、人物小传、概要、审核解释 | 旧称易混淆；型号差异大 | **作为中文写作/质检候选，先小流量验证** |

稳妥顺序：

1. 保留 DeepSeek 作为可计量默认基线。
2. 用 Kimi 测研究 / 长上下文 / 故事图，记录工具成功率、单任务调用数、截断与耗时。
3. 用 GLM 测中文改写 / 小传 / 质检解释，记录盲评、参数正确率与修复轮数。
4. MiniMax 继续少量复杂任务对照；不要把模型能力问题与网关/并发问题混为一谈。

至少收集 20 个相同输入、相同工具、相同预算的重复样本，再比：**参数正确率、一次交付率、重复修复次数、人工作品评分**。接入新 Provider 前检查工具调用、严格 JSON、流式、`finish_reason`、超时、Retry-After、usage/缓存字段与错误码。
