根据之前sessions的数据来看，之前确实存在多类“模型不断重试、Token 大量消耗”的情况，

## 1. 真正出现过的高消耗场景

### 1.1 门禁永远失败，模型反复改稿(初期问题已改，门禁都正常)

### 1.2 核心梗缺少字段，强采纳门禁反复卡死(部分shemca好像还是有问题)

曾经核心梗候选缺少 `motivation` 等必需字段。

模型每次都生成类似内容，但结构中仍然缺字段：

```text
生成核心梗
→ 强采纳要求 motivation
→ 缺失
→ 模型重新生成
→ 仍缺失
```

根因不是模型完全不会写，而是：

- Schema 没有提前把字段讲清楚；
- 门禁只在最后一步报错；
- 没有确定性字段归一化和兜底推导。

已经修复：

- 加入字段归一化；
- 缺失字段可以从已有内容确定性推导；
- 提示词和 Schema 同时说明必需字段；
- 采纳失败不再无条件重新生成整份内容。

---

### 1.3 `create_task_group` 丢失 `format`，Worker 反复崩溃

曾经任务组创建后没有正确传递格式字段，Worker 内部执行：

```js
format.toLowerCase()
```

但 `format` 是 `undefined`，于是：

```text
Worker 崩溃
→ 任务被租约回收
→ 重新入队
→ Worker 再次崩溃
```

如果重试没有计数，就会形成无限循环。

已经修复：

- 创建任务组时强制保留 `format`；
- Worker 多处增加空值防御；
- 重试次数持久化；
- 达到上限后进入失败态，不再自动循环。

---

### 1.4 重试次数没有正确计数，形成无限崩溃循环

这是最危险的一类。

以前某些失败路径只重新入队，但没有递增有效的 attempt 计数：

```text
任务失败
→ 重新入队
→ attempt 仍然是原值
→ 再失败
→ 再入队
```

表面上数据库里任务一直在运行，实际模型被反复调用。

已经修复：

- Job attempt 和实际 `run_start` 分开记录；
- 每次真正执行尝试都增加持久化计数；
- 达到 `maxAttempts` 后停止；
- 任务失败状态不能伪装成临时等待；
- 现在不能只看 `Job.attempts` 判断真实重试次数，还要看持久化 `run_start`。

---

### 1.5 `tool_search` 空转

这是之前真实测试里最明显的 Token 浪费来源之一。

模型不知道工具名称时，会不断调用：

```text
tool_search
→ 返回空
→ 换一个近义词继续搜索
→ 仍然为空
→ 再搜索
```

或者已经找到工具，却继续搜索，而没有真正调用工具。

最终表现是：

```text
tool_search × 多轮
→ 没有实际业务进展
→ 达到 MAX_TURNS
→ 返回“已达最大步数，请继续发消息”
```

真实个人助手测试就遇到过：

```text
get_project 只能返回概览
→ read_memory
→ tool_search
→ list_artifacts
→ 分页 list_artifacts
→ 继续翻历史
→ 最大步数
```

这次浪费的根因不是单纯模型不聪明，而是工具能力缺失：模型没有办法按 QA Run 直接读取审批凭据，只能通过遍历历史稿件猜测。

已经修复：

- 初始工具面缩小；
- `tool_search` 命中工具后，下一轮直接加入真实函数；
- 同一查询和重复空结果受到限制；
- `get_project(project_id, qa_run_id)` 可以直接查询指定审批记录；
- 真实 DeepSeek 复测已经从多轮分页搜索变成一次 `get_project`。

# 仍需注意：

- 如果模型本身坚持搜索，仍可能消耗若干轮；
- 但现在有 `MAX_TURNS` 和工具循环上限，不会无限进行。

---

### 1.6 长上下文导致重复读取和重复生成

之前主 Agent 获得了过多内容：

- 全项目历史；
- 多个 Agent 私有记忆；
- 很多旧 artifact；
- 全量工具定义；
- 旧的失败步骤；
- 当前任务无关的上下文。

模型容易出现：

```text
已经完成的任务重新做
已经读过的文件再次读取
旧版本和当前版本混淆
重复生成同类型候选
```

这会同时浪费：

- 输入 Token；
- 工具调用轮次；
- 输出 Token；
- 后续门禁和质量检查成本。

已经修复：

- 主 Agent 只拿当前项目共享事实、本会话指针和必要上下文；
- Agent 私有记忆独立；
- 子 Agent 只拿任务所需选段和版本；
- 稳定系统前缀和动态上下文分离；
- 工具结果做分段压缩；
- 压缩不能切断工具调用和工具结果的完整组。

---

### 1.7 上下文溢出后盲目重试

过去遇到：

```text
HTTP 400 context_length_exceeded
```

有些路径会把相同上下文再次发送，导致：

```text
同样的超长请求
→ 再失败
→ 再重试
```

这类重试几乎是纯 Token 浪费。

现在的逻辑是：

- 只有确认上下文确实缩小后，才允许再次调用；
- 压缩无效则直接失败；
- 保留用户指令、产物引用、完成证据和完整工具调用组；
- 不再用同一个超长上下文盲重试。

---

### 1.8 `pause → resume` 被错误计入失败重试

以前用户主动暂停后恢复任务，也会增加 attempt：

```text
正常任务
→ 用户暂停
→ 恢复
→ attempt 增加
→ 很快达到 maxAttempts
```

模型可能只调用了一次，但系统看起来像失败重试多次。

这会导致：

- 任务提前失败；
- 任务被错误重跑；
- 恢复时重新生成已经存在的内容；
- 额外消耗模型额度。

已经修复：

- 操作员主动恢复不再消耗失败重试次数；
- 崩溃恢复和人工暂停恢复分开计数；
- 恢复时读取 checkpoint，不从头生成。

---

### 1.9 Worker 崩溃、租约回收导致重复调用

曾经 Worker 静默退出或心跳丢失时：

```text
模型调用正在进行
→ Worker 失联
→ 租约过期
→ 任务被回收
→ 新 Worker 再次执行
```

问题在于，旧调用可能实际上已经成功，只是响应没有回到 Worker。

这会导致相同任务重复调用模型甚至重复写入。

已经修复：

- Worker supervisor 自动拉起；
- 租约强制校验；
- 记录 checkpoint；
- 未知写入结果不能盲目重试；
- 恢复前必须先核对已有产物；
- 写操作和只读操作采用不同重试策略。

---

### 1.10 供应商 429/502/529 多层重复重试

过去一次上游错误可能被多层同时重试：

```text
LLM Gateway 重试
→ HTTP Client 重试
→ Worker 重试
→ Job 重试
```

结果是一条失败请求被放大成多次甚至十几次请求。

尤其是：

- MiniMax 502；
- MiniMax 529 overloaded；
- 429 限流；
- 额度耗尽；
- 本地队列等待超时。

已经修复：

- API 作为并发治理唯一入口；
- Worker 不重复报告同一个限流；
- 只对明确可重试的请求重试；
- 已知额度、账户、权限错误不再盲目重试；
- Retry-After 统一处理；
- 本地容量等待不消耗 Job 失败次数；
- 重试次数和等待时间有上限。

仍然可能消耗 Token 的情况：

- 供应商确实返回了“可重试”的 502/529；
- 请求已经到达供应商并产生了部分计费；
- 这类请求无法保证零成本，只能通过限次数和退避控制。

---

### 1.11 502/529 被错误理解为模型失败

过去某些任务失败后，系统会重新生成内容，但实际是：

```text
模型没有收到请求
或供应商没有返回结果
```

错误流程是：

```text
上游网络失败
→ 当成写作失败
→ 让模型重新写一篇
```

这会造成一次无意义的内容重写。

现在已经区分：

- `provider_rate_limited`
- `local_queue_timeout`
- `context_length_exceeded`
- `invalid_model_response`
- `security_denied`
- `mutation_result_unknown`

不同错误进入不同恢复策略，不再一律让模型重写。

---

### 1.12 输出格式错误触发多次修复

MiniMax 曾出现：

- XML/DSML 工具调用不完整；
- JSON 被截断；
- 工具参数缺失；
- 空 content；
- 只返回思考没有正文；
- `<invoke>` 标签残缺。

旧逻辑可能不断要求模型重发。

现在已经改成：

- 当前轮内有限次数修复；
- 修复前保留原始任务；
- 不补猜缺失参数；
- 不执行半个工具批次；
- 达到修复上限后明确失败；
- 不用正则强行补全复杂嵌套标签。

因此，“未闭合标签”现在不是无限正则修复，而是结构校验 + 有界重试。

---

### 1.13 字数门禁贴边抖动

例如目标是：

```text
800–1200 字
```

模型可能连续生成：

```text
1201
1203
1205
```

旧逻辑：

```text
生成 → 1201 超限 → 重写 → 1203 超限 → 重写
```

已经修复：

- 增加合理软边界；
- 失败信息说明差多少字；
- 优先进行定向修订；
- 同一稿件使用版本更新，而不是新建重复稿件；
- 没有实际内容变化时不继续重跑。

---

### 1.14 错误产物类型导致编排反复补产物

曾经模型把正文保存成：

```text
type=other
```

而完成合同要求：

```text
type=manuscript
```

于是：

```text
产物已存在
→ Done Contract 找不到正确类型
→ 模型再次生成正文
→ 再生成一个错误类型
```

已经修复：

- 类型必须走 Ontology 映射；
- 期望类型错误时直接拒绝；
- 不允许通过 `other` 绕过完成门禁；
- 同一 run/type/title 尽量复用已有产物；
- 内容变更走版本更新。

---

### 1.15 真实测试中的重复创建和重复派单

过去测试环境还出现：

- 同名项目重复创建；
- 同一 Agent 重复派单；
- 旧运行没有清理；
- Fleet 成员重复进入；
- 多个 Worker 同时领取相同任务。

这些会产生大量重复模型调用。

已经修复：

- 项目、artifact、任务组增加幂等检查；
- 任务领取采用租约和数据库原子竞争；
- 父子任务有唯一 ID；
- 已完成产物不能被恢复流程重复计入；
- 失败子 Agent 不会被父任务包装成成功。

## 2. 历史上最严重的 Token 浪费路径

按照严重程度，大致是：

1. **门禁永远失败 + 重试不计数**
2. **Worker 崩溃 + 租约回收 + 重复执行**
3. **tool_search 空转**
4. **PA 工具能力不足导致分页遍历全项目**
5. **多层供应商重试叠加**
6. **长上下文重复读取和重复生成**
7. **上下文溢出后重复发送相同上下文**
8. **格式错误/JSON 错误无限修复**
9. **字数门禁贴边反复改稿**
10. **错误 artifact 类型导致任务认为没有交付**

之前一次完整真实编排验收中，记录到：

- 313 条真实调用/检查记录；
- 输入约 3,696,780 tokens；
- 输出约 155,793 tokens。

这不是全部都属于浪费，其中包含真实工作和验收，但也说明错误重试、失败检查和长上下文会显著放大成本。

## 3. 目前已经有的防浪费措施

现在系统主要通过以下方式控制：

- 单轮 `MAX_TURNS`；
- 工具搜索动态加载；
- 工具搜索空转限制；
- 模型协议修复次数上限；
- 上下文压缩前后实际大小检查；
- Provider 重试上限；
- Job 最大尝试次数；
- 任务租约和 fencing；
- 写操作不盲重试；
- 未知写入结果先核查；
- 产物版本和 CAS；
- 任务、项目、artifact 幂等；
- 只读和写入使用不同 retry policy；
- 失败状态和临时等待状态分离；
- 达到预算后先压缩，没有进展才终止；
- 缓存前缀稳定化；
- Agent 私有记忆与项目共享记忆分离；
- 子 Agent 精确上下文；
- 真实 Token、耗时、缓存命中独立记录。

## 4. 仍然可能出现 Token 浪费的地方

目前不能说所有浪费路径都已经消失，仍有几个风险：

### 4.1 模型坚持错误工具路线

例如工具已经返回错误，但模型仍继续尝试类似工具。现在有轮次上限，但仍可能浪费几轮。

### 4.2 供应商已经接收请求但响应失败

如果 MiniMax/DeepSeek 已经开始计算，随后网络断开，系统无法判断供应商是否计费。此时只能避免盲目写重试，不能保证供应商侧完全不扣费。

### 4.3 完整 Worker 测试仍有历史失败

当前针对性测试已经通过，但完整 Worker 基线仍有 17 项失败，涉及 batch、replay、critic、length、context。这些路径还需要单独确认是否存在隐藏重复调用。

### 4.4 长任务模型本身反复改写

如果用户要求非常模糊，模型可能主动生成多个版本、反复自检。系统可以限制预算，但无法完全替用户决定什么时候内容“足够好”。

### 4.5 GRPO/DPO 训练尚未启用

目前没有用线上奖励模型自动训练，因此不会出现训练反馈把坏的重试策略放大的问题。但未来启用 RL 时，必须把以下行为纳入负奖励：

- 无进展工具调用；
- 重复读取；
- 重复生成相同 artifact；
- 未经授权重试写操作；
- 忽略已返回的错误；
- 在没有新证据时重复质检。

## 5. 最终判断

之前的“大量 Token 不断重试”并不是单一问题，而是几类问题叠加：

```text
错误的门禁条件
+ 不完整的工具能力
+ 重试计数缺失
+ 租约/Worker 状态不一致
+ 上下文过大
+ 多层 retry 叠加
+ 模型工具选择空转
```

目前最危险的无限循环已经被限制或修复，尤其是：

- 门禁死循环；
- 重试不计数；
- Worker 崩溃反复领取；
- `tool_search` 空转；
- QA 查询遍历全部稿件；
- 上下文溢出盲重试；
- 写操作未知结果盲重试。

但在后续继续开发时，任何新增 Agent、Tool、Gate 或 Provider，都必须同时增加：

1. 是否幂等；
2. 是否可重试；
3. 最大重试次数；
4. 是否产生副作用；
5. 是否需要先核查；
6. 是否计入 Token 预算；
7. 无进展时如何停止；
8. 失败后能否恢复而不从头生成。

否则很容易重新引入“模型看起来在工作，实际只是在不断消耗 Token”的问题。
