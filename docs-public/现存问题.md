# 现存问题与下一步

> 更新：2026-11-21。这些不是「项目完全不可用」的致命 Bug，而是从 Early Preview 走向稳定生产还需要解决的事项。  
> 根 README「技术债与下一步」详表已迁入本文；产品总览见 [`README.md`](../README.md)。

按作者的开发经历，这个项目曾由 **六个 Cursor 窗口同时推进**。这带来了密集的功能覆盖，也留下了共享契约漂移、重复实现、历史路径与文档不同步的问题。这是开发背景，不是对每个 Bug 因果的证明；下表将已经观察到的风险与后续验收方向分开。

项目的价值不在于声称没有技术债，而在于它已经开始把「看起来跑完了」拆成可检查的步骤：谁获得执行权、发了什么上下文、工具是否落盘、哪个版本通过了哪个检查。

**判断**：核心架构已经能跑，主要遗留的是生产化、可观测性、长跑稳定性和质量评估，而不是多智能体主流程完全设计错误。已经发生过修复的故障不应重复包装成「全部待做」；已有单元测试也不等于「全面生产验证」。

## 2. 分项说明（11 月 21 日整理 + README 增补）

### P0

1. **工具参数、Schema、Skill、前后端 DTO 仍可能漂移**  
   多智能体链路层次很多，同一个字段在不同层命名或结构不一致时，模型会反复修复或被另一层拒绝。Cursor 经常出现同一字段 snake_case / camelCase 不分，部分字段没对齐（如 `input_schema` 与 `inputSchema`）。

2. **缺少完整的 Provider / 账号级请求尝试日志**  
   目前无法严格计算每个供应商的真实 RPM、429 比例、重试放大倍数和实际在途数。161 条 429 只能算诊断数据，不能算真实限流概率。口径说明见 [模型选型 / 限流](./模型选型限流并发与自动回复.md)。

3. **写操作的幂等与未知副作用边界还需要继续加固**（部分修复）  
   如果工具已经写入但响应在网络断开时丢失，系统仍可能再次写入或生成重复产物。

### P1

4. **连续重复错误后的策略升级还不够完善**  
   模型可能反复搜索、换参数、重试相同工具，却没有实质交付。需要按错误指纹触发停止、换路径或请求人工介入。

5. **成本链路还不能完全追踪到单次真实调用**  
   目前还不能稳定做到 `task → run → logical_call → attempt → tool → provider billing`。总编、子 Agent、搜索、重试和改稿可能被分散统计；部分后台任务与部分 Agent 尚未纳入统计。

6. **缺少严格的同题模型 A/B 和人工盲评体系**  
   目前能证明「能启动、能过 Schema、能产物落库」，但还不足以证明 DeepSeek、MiniMax、Kimi、ChatGLM 等谁的作品质量更高。

7. **运行时与工具模块仍偏巨大**  
   多个 Cursor 窗口同时修改同一批核心文件，后续容易出现隐性耦合、重复实现和回放兼容问题。

8. **测试与真实作品数据隔离不足**（自 README 迁入）  
   当前 Session 混合 E2E、恢复、脚手架和真实生成；报告难以排除故意失败与重复采样。

### 生产化 / 长跑（原编号续）

9. **API 和 Worker 的常驻进程管理还没有产品化**  
   之前已经出现过 Worker 静默退出、租约回收和长任务中断。手动启动可以运行，但 launchd、Supervisor、健康探针和自动恢复仍需完善。

10. **完整端到端证据还不够覆盖所有场景**  
    目前有多种 Agent、格式和 MiniMax/DeepSeek 实测，但「两章正文长跑、六格式持续运行、飞书长期代操作」等并非每次都有最新完整证据。

11. **SSE 长连接、断线重连和超时策略还需长期压测**  
    历史上已经修复过 `datetime` 导致 SSE 中断的问题，但长时间流式响应、浏览器断网恢复、重复事件和前端状态补偿仍需持续验证。

12. **SQLite 的生产扩展、备份和迁移策略不足**  
    当前数据量已经较大，`NullPool + busy_timeout` 缓解了并发问题，但在线备份、迁移回滚、数据库锁监控和多实例部署仍不完善。

13. **模型能力和供应商策略仍缺少统一治理**  
    弱模型可能产生占位符、错误产物类型或空内容；MiniMax 可能遇到 429/502/529/额度耗尽，DeepSeek 也有自己的并发和配额边界。现有门禁和重试能缓解，但不能保证所有模型都可靠完成复杂长任务。

14. **多项目并发与硬件长跑观测不足**（自 README 迁入，P2）  
    M4/32GB 的 8/12 路建议尚不是负载认证；需要同步采集资源与成功交付吞吐。

15. **历史默认值与陈旧文档清理**（自 README 迁入，P2）  
    旧模板、README、包说明仍可能互相矛盾；需要统一启动说明、模型默认、执行路径与链接检查。

## 3. Session 暴露的问题与防线

可以显著降低错误发生与扩散的概率，但不能保证模型不犯错。右栏是改进方向，**不等于当前版本必现故障**。

| Session 暴露的问题 | 当前已有防线 | 接下来值得完善 |
| --- | --- | --- |
| 布尔值变字符串、JSON 不完整、字段放错层级 | 参数校验、有限格式修复、无效输出拒绝执行；总编工具批次先验后执行 | 从同一业务 Schema 生成模型参数、示例与校验器；减少宽泛 `Any` |
| 收到报错仍重复同一参数 | 结构化错误、下一步提示、错误计数、停滞与预算边界 | 按「工具 + 错误路径 + 参数摘要」去重；重复失败后换策略或升级处理 |
| 忙于检索和调评分参数，却不交付 | Done Contract、产物/门禁进度检查、有界轮次 | 在每轮显式给出剩余交付缺口，以目标进展而非调用数量衡量执行 |
| 模型自称完成或自评通过 | 持久化产物、版本、独立 Gate 与完成收据 | 增加同题盲评与外部可复核的质量证据，避免迎合检查而牺牲作品 |
| 长上下文忘记约束、混用旧版本 | 项目事实、来源引用、版本、Slot、压缩与 Handoff | 回归测试覆盖压缩前后、改稿与跨 Run 引用；防止摘要悄悄改写事实 |
| 工具已经写入，但响应丢了 | 写操作账本、幂等/版本控制、in-doubt 恢复策略 | 更完整地关联请求、写入回执和恢复决策，不盲目重放副作用 |
| 429 后重试、排队和切模型互相放大 | 请求闸、租约、冷却、Retry-After、有界重试与可选备用 | Provider/账号级 RPM、TPM、突发预算，让网关内部重试也统一入场 |
| 多 Agent 相互转述，不清楚依据 | 子任务隔离、限定工具、来源/版本引用、回执与报告分开 | 扩充错误委派、失效引用、子任务失败后父任务处理的端到端回归 |

## 4. 始终交给作者的部分

工程能拒绝错误参数、阻止无证据完成、控制错误扩散，却不能保证审美、亲历感、原创性、长篇情感弧线与市场判断。去 AI 味检查不是来源鉴定；结构门禁不是文学评分；付费平台规则与合规结论仍需按最新信息人工核验。

3 工具返回本身过大时，第一轮仍可能较大

工具结果裁剪发生在进入后续上下文前。工具本身返回的那一轮仍可能较大，尤其是：





全量 artifact 列表；



大段知识库正文；



多页记忆；



旧项目历史；



网页搜索结果。

因此现在更推荐使用：

search → snippet → read exact range

而不是直接调用全量列表或全量读取。

5.4 模型坚持错误工具路线时仍会浪费几轮

例如：

tool_search
→ 空结果
→ 换关键词
→ 再搜索

现在有：





MAX_TURNS



空转限制；



初始工具面收窄；



失败结果记录。

但不能保证模型一轮就做出最佳工具选择。

5.5 撤权后的派生上下文重建还不是全覆盖

当前已经限制新请求不能继续使用失效权限，但如果旧摘要、子 Agent 结果或缓存中混入了被撤权内容，完整的全路径重建仍属于后续增强项。
