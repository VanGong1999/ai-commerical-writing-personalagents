下面是这条会话中暴露过的问题、根因、处理结果和未解决事项汇总。

## 一、已经发现并修复的问题

| 问题 | 主要原因 | 已采取的修改 |
|---|---|---|
| `DeepMethodPanels.tsx` 中 `trim` 报错 | 数组过滤时直接对可能为 `undefined` 的字段调用 `.trim()` | 增加空值处理，统一使用安全字符串归一化后再过滤 |
| AI 用量明细只有“幕僚长”有数据 | 用量统计只绑定了 Supervisor/Chief，没有按 147 个 Agent、Bot、子 Agent 归属记录 | 补充 Agent、Bot、任务、子任务、模型、项目维度的用量归属和明细结构 |
| DeepSeek 连调漫剧主线编组没有对应内容 | Agent 目录、Bot 绑定、漫剧主线编组之间的 ID 和上下文没有完全贯通 | 统一 `bot_id = agent_id`，补充岗位绑定、上下游关系和真实工具调用链 |
| AI 同事提示词缺少审批状态边界 | 总编提示词有规则，但普通 AI 同事和讨论交接使用了另一套系统提示 | 抽取统一的 `APPROVAL_STATE_AUTHORITY`，注入总编、普通同事、讨论交接、个人助手 |
| 把旧文档“待确认”误判为当前状态 | 模型读取历史文档文字，没有优先查询持久化 QA/审批记录 | 现在要求以指定 QA Run 的签阅凭据、来源版本和当前版本对照为准 |
| 没有有效凭据时模型自行推断已确认 | 旧文档、candidate 标签、模型自述被当成审批凭据 | 缺凭据、版本变化、来源失效、越权时只能返回“待确认”，不能自行放行 |
| `get_project` 只能返回项目概览 | 工具没有支持按 QA Run 精确读取 `pipelineQaApprovals` | 增加 `get_project(project_id, qa_run_id)`，只返回指定 QA 的签阅、来源、报告和当前版本 |
| 个人助手真实测试不断翻历史稿件，最后达到最大步数 | 模型无法直接查询指定 QA 记录，只能调用 `list_artifacts` 分页搜索 | 增加精确 QA 查询后，真实 DeepSeek 已只调用一次 `get_project` 完成核对 |
| 个人助手可能读取其他项目的 QA 信息 | 项目归属校验不完整 | 增加 owner/project 权限校验，跨项目不能读取审批详情 |
| AI 同事讨论交接没有审批规则 | `discussion_prompt` 使用独立的简化提示 | 新增专用 `discussion_system_prompt`，保留审批边界但不授予额外工具权限 |
| 精简岗位/Scoped Agent 的提示不完整 | Scoped 分支使用短提示，未包含完整审批状态规则 | 在不扩大工具权限、不注入无关上下文的前提下补充固定规则 |
| 门禁过严，关键词误判 | 把主观建议、风格意见、历史描述和硬性审批条件混在同一门禁 | 质量评测和风格建议改为 advisory；真正阻断只依赖权限、版本、审批、来源等客观凭据 |
| “待确认”被当作永久状态 | 没有区分历史描述和当前状态 | 提示词中明确：历史状态只代表记录时点，当前状态必须重新核对有效凭据 |
| watchdog 提示订阅未释放 | 任务终态、订阅租约、取消流程之间存在边界不一致 | 增加终态释放、重复停止拒绝、暂停后不再发起新模型调用等收尾逻辑 |
| 长上下文容易漂移 | 主 Agent 获得了太多项目历史、岗位记忆和无关工具信息 | 按任务、项目、岗位、会话拆分上下文；共享记忆和私有记忆分离；稳定前缀优先 |
| Prompt Cache 命中率不稳定 | 动态时间、任务、项目状态等内容混入缓存前缀 | 静态系统规则、工具协议、岗位身份固定在前缀；动态事实放到后续 section |
| 子 Agent 收到过多上下文 | 主 Agent 没有做任务级上下文裁剪 | 子 Agent 只接收绑定稿件版本、选段、任务目标和必要约束，不接收全项目历史 |
| 工具命名导致调用不准确 | 存在 `tool_search`、`search_tools`、`invoke_tool`、`tool_invoke` 等旧别名 | 保留兼容旧工具，但新路径统一优先 `tool_search`，命中后下一轮直接调用真实工具 |
| 工具调用发现效率低 | 模型开始时看到全部工具，容易误选或增加上下文 | 初始只暴露核心工具，未知能力通过搜索动态加载 |
| “正则修复未闭合标签”可能引入错误 | 正则无法可靠处理嵌套、属性、转义和部分输出 | 没有把正则修复作为通用放行机制；当前更强调结构化输出校验、失败重试和明确错误边界 |
| 任务无法断点续传 | 运行状态、步骤、版本和写入指针没有形成完整恢复凭据 | 增加运行步骤、版本、CAS、暂停/恢复、幂等和终态记录 |
| 后台任务可能卡死 | 缺少可靠的租约、最大轮次、取消和恢复边界 | 增加 watchdog、最大轮次、任务状态、暂停、取消和续跑机制 |
| AI 写作缺点被一刀切误判 | 关键词规则直接阻断，没有区分建议和硬错误 | 大部分写作问题改成可选提醒；只有明确违规、版本冲突、权限问题才阻断 |
| 反馈无法形成个性化闭环 | 用户不一定填写退稿原因、编辑成本、收入等字段 | 反馈字段允许为空，缺失保留 `unknown`；用户明确表达时自动记录原话并关联作品版本 |
| 旧历史修改影响当前稿件判断 | 历史产物和当前版本没有绑定 | 增加 artifact version、QA Run、来源版本、报告版本对照 |
| 多租户架构与本地单用户方案不匹配 | 早期按 SaaS 多租户设计，后来改为本地 SQLite | 当前按单用户本地助手处理，没有继续引入 PostgreSQL 多租户复杂度 |
| 真实模型测试曾与模拟测试混用 | 早期部分测试使用 mock，用户要求改为真实 DeepSeek | 关键验收改用真实 DeepSeek Flash；mock 仅用于快速单元测试 |
| API/Worker/飞书/Scheduler 进程曾不在运行 | 服务被停止或测试期间进程退出 | 已按原项目命令恢复 API、Agent Worker、通用 Worker、飞书和 Scheduler |

## 二、真实测试中暴露出的关键问题

### 1. 第一次个人助手真实测试没有成功完成核对

当时模型只获得了项目概览，没有 QA 详情，于是：

1. 调用 `get_project`；
2. 读取项目记忆；
3. 搜索工具；
4. 分页调用 `list_artifacts`；
5. 不断翻历史稿件；
6. 最后达到最大步数。

这不是模型本身唯一的问题，核心是工具能力不足。现在已经增加：

```text
get_project(project_id, qa_run_id)
```

第二次真实 DeepSeek 测试已经验证：

- 只调用一次 `get_project`
- 正确读取指定 QA Run
- 正确核对三份来源和两份报告的版本
- 明确旧 LogicAck 文字不能覆盖现行凭据
- 明确 QA 签阅不等于发布授权
- 没有写稿、改数据、派单或重新申请确认

## 三、当前已经形成的正确判断规则

现在系统应该按以下优先级判断状态：

```text
当前有效 QA/审批凭据
    >
来源和稿件当前版本对照
    >
项目持久化状态
    >
历史文档中的状态描述
    >
模型自述、candidate 标签、关键词推断
```

所以：

- 历史文档写“待确认”，不能直接推断当前仍待确认；
- 历史文档写“已通过”，也不能直接推断当前仍有效；
- 当前版本和签阅版本不一致，必须重新确认；
- 缺少凭据时必须提示待确认；
- QA 签阅不代表发布授权；
- 模型不能自行签字、放行或重新发起审批。

## 四、目前仍未完全解决的问题

### 1. 完整 Worker 测试仍有历史基线失败

已有针对性测试通过，但完整 Worker 测试基线仍是：

- 353 项通过
- 17 项失败

这些失败主要涉及：

- batch
- replay
- critic
- length
- context

其中部分失败在修改前源码上也能复现，因此没有把它们误判成这次修复引入的问题。但它们仍然属于技术债，不能说整个 Worker 测试矩阵已经全绿。

### 2. 不能保证模型永远不误读

当前已经通过：

- 系统提示
- 工具设计
- 服务端权限校验
- 版本校验
- QA 凭据校验
- 低上下文设计

降低误读概率。

但模型仍可能：

- 忽略工具调用要求；
- 错误总结已返回的信息；
- 把建议写成结论；
- 在工具失败后给出不够谨慎的自然语言。

因此，真正的发布、采纳、审批仍然必须由服务端门禁控制，不能只依赖提示词。

### 3. 完整撤权后的派生上下文重建仍未完成

当前已经限制：

- 子 Agent 只能收到必要上下文；
- 私有记忆和共享记忆分离；
- 跨项目读取被拒绝。

但如果某个 Agent 曾经看过一份资料，之后被撤权，系统还没有完全实现所有派生摘要、缓存、子 Agent 结果的全路径重建和撤销。这仍属于设计范围内的后续工作。

### 4. 商业反馈闭环尚未有真实业务数据验证

系统已经支持：

- 退稿原因为空；
- 编辑修改成本为空；
- 收入为空；
- 投稿状态为空；
- 用户原话自动记录；
- 按作品版本关联反馈。

但目前还没有足够真实的：

- 投稿成功/失败数据；
- 编辑修改耗时；
- 退稿原因；
- 实际收入；
- 长期个性化提升结果。

所以现在只能说“数据结构和入口已准备好”，不能说商业化效果已经被证明。

### 5. DPO/GRPO 尚未进入在线训练

按你的决定：

- GRPO 相关能力保留；
- 暂时不在线运行 GRPO；
- 当前没有可靠的长期奖励数据；
- 也没有足够稳定的人工偏好标注集。

目前更适合先积累：

- 用户采纳/拒绝；
- 修改距离；
- 退稿原因；
- 编辑成本；
- 作品完成率；
- QA 通过率；
- 发布后的商业结果。

等数据稳定后再考虑 DPO 或 GRPO。当前贸然训练会把主观偏好、错误门禁和历史误判一起强化。

### 6. 真实供应商账单和训练效果尚未验证

系统可以记录：

- 输入 token；
- 输出 token；
- 缓存命中；
- 缓存未命中；
- 模型；
- Agent；
- 项目；
- 任务。

但这些数据不能直接等同于供应商最终账单，尤其是：

- DeepSeek/Minimax 的实际计费规则；
- 缓存价格；
- 重试和失败请求；
- 供应商侧折扣；
- 异步请求结算。

### 7. 发布授权仍然独立于 QA 签阅

当前真实测试中，三稿和两份报告的 QA 版本均匹配，但系统仍正确返回：

```text
QA 签阅不等于发布授权
```

这不是缺陷，而是有意保留的安全边界。若要允许自动发布，需要单独设计：

- 发布授权凭据；
- 发布渠道；
- 发布版本；
- 发布人；
- 发布时间；
- 撤回和回滚机制。

### 8. 供应商私有推理无法完整回放

系统可以记录：

- Agent 步骤；
- 工具调用；
- 工具返回；
- 中间状态；
- 版本；
- 任务状态；
- 恢复点。

但无法完整记录供应商内部的：

- 隐藏推理；
- 内部重排；
- 模型采样细节；
- 供应商内部重试；
- 外部系统不可逆操作。

因此“全过程可见”目前准确含义是：产品可观测的 Agent 过程可见，不等于供应商内部推理完全可见。

## 五、现在最重要的结论

目前“旧文档中的待确认状态被误当作当前状态”这一类问题，已经在：

- 总编；
- AI 同事；
- 精简岗位；
- 子 Agent；
- 讨论交接；
- 个人助手；
- QA 查询工具；
- 服务端版本门禁；

这些层面完成了补强。

现在系统的正确行为是：

> 历史文档只作为历史描述；当前状态必须以指定项目、指定 QA Run、有效审批记录和当前稿件版本对照为准。任何缺失、失效、越权或版本不一致，都只能提示待确认，不能由模型自行放行。

剩余工作主要集中在完整 Worker 基线失败、撤权后的派生上下文重建、真实商业反馈积累、发布授权独立流程，以及后续 DPO/GRPO 训练数据准备，而不是这次“旧待确认状态误读”本身。
